# Deploying without shell access (cPanel)

The target for this document is a shared host where you have **FTP or cPanel File
Manager, phpMyAdmin and Cron Jobs — and nothing that can run a command**: no
shell, no CLI installer, no web installer. Everything below follows from that one
constraint.

The rule: **every deployment concern is either a file you copy or a cron job that
reconciles.** Nothing needs an interactive step, and nothing needs PHP to be run
by hand on the host.

```
workstation                                   cPanel
  php bin/build-deploy.php   ── two zips ──▶  File Manager: upload + extract
  (manifest, content, SPA)                    phpMyAdmin: one optional paste
                                              Cron Jobs: three entries
                                              Browser: /v1/health
```

## 1. The two directories

| Directory | Absolute path (example) | Contents |
| --- | --- | --- |
| Document root | `/home/USER/public_html/boardsim.example.net` | `.htaccess`, `app/`, `api/index.php`, `api/backend.php`, `robots.txt`, `sitemap.xml`, `llms.txt` |
| Backend | `/home/USER/boardsim-app` | `src/`, `content/`, `engine/`, `requirements/`, `scenarios/`, `bin/`, `migrations/`, `public/api/index.php`, `config.local.php`, `release.json` |

The backend is a **sibling of `public_html`**, so Apache can never serve it. It is
not an option to put it inside the document root "for convenience": it contains
the scenario corpus, the regulatory register and the configuration pointer.

### How the document root reaches the backend

The document root is an **Apache** boundary, not a **PHP** one. `require` takes a
filesystem path, so `api/index.php` (the shim) loads the real front controller
from outside the docroot:

```
.htaccess rewrites /v1/* → api/index.php
api/index.php  ── requires api/backend.php ──▶ '/home/USER/boardsim-app'
               └─ requires /home/USER/boardsim-app/public/api/index.php
                  └─ $root = dirname(__DIR__, 2) → reads src/, content/, scenarios/
```

`api/backend.php` is generated by the build. It contains one absolute path and no
secret, and `public/.htaccess` denies it over HTTP while `require` still reads it.

There are exactly **two pointers**, and they are deliberately separate:

| Pointer | Lives | Written by | Holds |
| --- | --- | --- | --- |
| Where is the backend? | `DOCROOT/api/backend.php` | `bin/build-deploy.php` | a filesystem path |
| Where are the credentials? | `BACKEND/config.local.php` | you, once, from `config.local.php.example` | `dsn` / `user` / `pass` (or a `secrets_file` path) |

If `open_basedir` prevents PHP from reading the backend, `/v1/health` answers
`BACKEND_NOT_FOUND` and reports the effective `open_basedir`. The alternative is
`'layout' => 'flat'`: build with it, set the DocumentRoot to
`<backend>/public`, and no pointer is needed at all.

## 2. Parameters

Nothing host-specific is committed. `deploy/host.config.example.php` documents the
keys; `deploy/host.config.php` is gitignored and holds the real target:

```php
return [
    'layout' => 'split',                                       // or 'flat'
    'account' => 'USER',
    'domain' => 'boardsim.example.net',
    'docroot' => '/home/USER/public_html/boardsim.example.net',
    'backend' => '/home/USER/boardsim-app',
    'secrets_file' => null,                                    // inline creds otherwise
    'db' => ['name' => 'USER_boardsim', 'user' => 'USER_boardsim'],
    'php_binary' => '/usr/local/bin/php',
    'cron' => ['migrate' => '*/10 * * * *', 'purge' => '15 3 * * *', 'verify' => '30 3 * * *'],
];
```

`bin/build-deploy.php` refuses to build while a placeholder is present, while the
backend is inside the docroot (or vice versa), or while the specification or the
content bundle fails verification.

## 3. First deployment

1. **Build** on the workstation:
   `php bin/build-deploy.php --version=1.2.0`
   → `build/deploy/boardsim-1.2.0/{docroot,backend}/`, `docroot.zip`, `backend.zip`,
   `install.sql`, `cron.txt`, `verify.txt`, `README.txt`.
2. **Database**: cPanel → MySQL Databases → create the database and user, attach
   with privileges. (cPanel prefixes both with the account username.)
3. **Backend**: upload `backend.zip` and extract it into `/home/USER/` so the
   folder becomes `/home/USER/boardsim-app`.
4. **Credentials**: copy `config.local.php.example` to `config.local.php` and fill
   in the password. This is the only file you type on the host, and it is outside
   the document root.
5. **Document root**: upload `docroot.zip` and extract it into the subdomain's
   document root. It must end up holding `.htaccess`, `app/`, `api/`, `robots.txt`,
`sitemap.xml` and `llms.txt` — the last three at the root, not inside `app/`, or no
crawler will find them.
6. **Schema**: either paste `install.sql` into phpMyAdmin (instant), or let the
   migrate cron job do it within one tick.
7. **Cron**: paste the three lines from `cron.txt` into cPanel → Cron Jobs. Use
   the PHP binary for the **same version the domain runs**; a cron defaulting to a
   different major version parses the code with a different interpreter.
8. **Verify**: open `https://boardsim.example.net/v1/health`, then run the line in
   `verify.txt` from the workstation.

Before uploading, prove the artefact locally:

```bash
php -S 127.0.0.1:8200 -t build/deploy/<version>/docroot deploy/smoke-router.php
php bin/verify-deploy.php --base=http://127.0.0.1:8200 --require-ready
```

Set `BOARDSIM_DEV=1` for the server process if the workstation has no MySQL; the
check accepts `mode=dev` on a loopback origin. This runs 19 assertions against the
built trees — routing, SPA shell and asset hash, CSP, dotfile denial — so a
packaging mistake is caught before it becomes a cPanel upload.

## 4. `/v1/health` is the installer

There is no install page, so health carries the deployment state. It answers even
when the database is missing, which is the point.

```json
{ "status": "ok | degraded",
  "deployment": {
    "release": { "version": "1.2.0", "sha256": "…", "commit": "…" },
    "database": { "reachable": true, "schema": "ok|partial|missing|unknown", "applied": ["001_init.sql"] },
    "bundles": { "seeded": 3, "expected": 3, "missing": [] } } }
```

`deployment.database.hint` names the fix: run the migrate cron, or paste
`install.sql`. Other routes answer `503 DB_UNAVAILABLE` with a short reason code
(`missing_config`, `unknown_database`, `access_denied`, `unreachable`) instead of a
blank 500.

## 5. The reconciliation cron job

`bin/migrate.php` is idempotent and safe at any frequency:

- applies any `migrations/*.sql` not present in `schema_migrations` — including
  `004_rate_limits.sql`, which the rate limiter needs;
- records each migration, so an older copy of a file cannot hide;
- seeds the three pinned `content_bundles` rows (required before the first run:
  `runs.policy_sha256` is a foreign key to them);
- takes `GET_LOCK('boardsim_migrate')`, so overlapping ticks no-op.

## 5a. Rate limits

The product has no login, which means one POST creates a run and writes rows. The
front controller therefore applies a fixed one-minute window per client address
and action (`src/Http/RateLimiter.php`):

| Action | Requests per minute | Applies to |
|---|---:|---|
| `run_create` | 10 | `POST /v1/runs` |
| `decision` | 30 | decisions, board pack, run deletion, unknown writes |
| `share` | 10 | share minting and revocation |
| `read` | 120 | catalogue, health, glossary, explanations |

A refused request answers `429` with `RATE_LIMITED` and a `Retry-After` header. The
table stores a SHA-256 digest of the client identity, never the address, and rows
from finished windows are swept opportunistically. If `rate_limits` is missing or
the counter query fails, the limiter **fails open** and logs — availability of the
exercise matters more than the limit, and `/v1/health` reports `schema: partial`
until the migration runs.

Run it every ten minutes on install day, then `0 2 * * *`. `--check` reports
without writing. It exits non-zero, with the reason, if the database user lacks
DDL privileges — in that case apply `install.sql` in phpMyAdmin instead.

## 6. Re-deploying and rolling back

Re-deploy is steps 3, 5 and 8: extract the new zips over the old trees. The
pointer is regenerated identically, `config.local.php` is untouched, and the
database is only ever added to. Keep the previous version's zips on the host;
rolling back is re-extracting them.

Upload `app/` before `index.html` if you want to avoid a few seconds where the old
shell references an asset that no longer exists.

## 7. What only the host can verify

- `.htaccess` (routing, CSP, HSTS, dotfile denial) is only truly exercised by the
  real Apache. `php -S` ignores it; `deploy/smoke-router.php` mirrors it for the
  pre-upload smoke test but cannot prove `AllowOverride All` is set.
- MySQL grants and the optional append-only trigger: cPanel usually offers only
  ALL PRIVILEGES per database, so `integrity_controls` may truthfully stay
  `["hash_chain"]`. Add the triggers in phpMyAdmin if `TRIGGER` is permitted, then
  reflect it in `/v1/health` and the methodology page.
- AutoSSL: changing the subdomain's document root invalidates a pending
  validation, so re-run it afterwards.
